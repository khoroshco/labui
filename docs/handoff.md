# HANDOFF для Claude Code — вынести Banner Lab DS в независимый репозиторий

Читателю (Claude Code): это инструкция, как превратить текущий набор `*.dc.html` + `tokens.css`/`ds.css` в **самостоятельную библиотеку дизайн-системы**, которую потребляют несколько сервисов. Ключевой контекст: **весь код (и в ДС, и в сервисах) пишет AI, ревью человеком НЕ будет.** Значит надёжность держится на автоматике: типы, тесты, линт, визуальная регрессия, a11y-гейты, семвер и CI, который блокирует мёрж при любом красном.

Не переписывай компоненты «под фреймворк» бездумно — сначала подними инфраструктуру вокруг ТЕКУЩЕГО рантайма (см. §2 «Стратегия»), потом эволюционируй.

- **Общие правила/состояния**: `ds.css` (шрифты, фокус, пресс, тултипы, reduced-motion, keyframes).

- **Компоненты** (27, формат Design Component: `<x-dc>`-шаблон + класс `Component extends DCLogic`, рантайм в `support.js`):

## 2. Стратегия: не ломать рантайм, обвязать надёжностью

Переписать всё на React сразу — рискованно (AI-only, без ревью) и преждевременно: сравнивать будет не с чем. Порядок действий — от дёшево-надёжного к глубокому:

1. **Заморозить контракт**: `CLAUDE.md` + типы пропсов (`data-props` уже несут `tsType`) — сделать их машиночитаемыми и проверяемыми (§5).
2. **Гейты в CI** поверх текущего формата (smoke + a11y + visual + линт токенов) — ловят регресс без переписывания.
3. **Пакет для потребителей** (`dist/`) — как сервисы это подключают (§6).
4. Затем — миграция рантайма на React. Она **решена**, а не условна (причина: `support.js` — сгенерированный рантайм, исходников которого у нас может не быть, то есть неконтролируемая внешняя зависимость). Делается по одному компоненту через паритетный харнесс: см. ROADMAP, Фаза 3. Порядок именно такой, потому что харнессу нужны заранее замороженный эталон, `api.json` и покрытые инварианты.

## 4. Надёжность №1 — smoke-тест «грузится без ошибок»

Самый дешёвый и самый ценный гейт для AI-only. Playwright открывает каждый `*.dc.html`, ждёт рендер, падает на **любой** `console.error`/`pageerror`/незагруженном ресурсе (ловит именно те гонки и битые пути, что мы уже встречали).

```js
// tests/smoke/all-components.spec.ts
import { test, expect } from '@playwright/test';
import { globSync } from 'glob';
for (const file of globSync('src/**/*.dc.html')) {
  test(`loads clean: ${file}`, async ({ page }) => {
    const errors = [];
    page.on('console', m => m.type() === 'error' && errors.push(m.text()));
    page.on('pageerror', e => errors.push(String(e)));
    page.on('requestfailed', r => errors.push('404 ' + r.url()));
    await page.goto('http://localhost:5173/' + file);
    await page.waitForTimeout(800);          // добить асинхронные маунты/хелперы
    expect(errors, errors.join('\n')).toEqual([]);
  });
}
```

## 5. Надёжность №2 — контракт пропсов и токенов машинно

AI легко «дрейфует», поэтому правила из `CLAUDE.md` надо ПРОВЕРЯТЬ, а не только описывать.

- **`scripts/check-tokens.mjs`**: грепает `*.dc.html` на литеральные `#hex`, `rgb(`, `cubic-bezier(`, `px`-значения вне разрешённых мест → фейл со списком. (У нас правило: цвет/изинги/шкалы — только токенами.)
- **`scripts/check-props.mjs`**: парсит `data-props` каждого компонента и его шаблон/логику; фейлит, если проп объявлен, но нигде не читается, или читается `this.props.X`, но не объявлен. Гейт не теоретический — он реально ловил: `Input.nums` (объявлен, не читался), `Disclosure.separator` (сепараторами владеет контейнер), `CycleButton.hov` (значение считалось в пустоту), `InputRow.tint` (читался, но не объявлен — невидимый для редактора канал между компонентами).
- **Типы для потребителей**: из `data-props.tsType` сгенерировать `dist/types.d.ts` (по одному интерфейсу пропсов на компонент). Тогда сервисы получают автокомплит и `tsc` ловит неверные вызовы.
- **Snapshot API-контракта**: `scripts/snapshot-api.mjs` пишет `api.json` (имя → пропсы/типы/дефолты). CI фейлит на изменение без записи ченджсета — так «случайное» переименование пропа (в истории: `onAccent`→`inverse`, `snap`→`snapStep`, `action`→`actionLabel`, `active`→`value`) не проедет молча.

## 5а. Инварианты, которые уже ломались — закрыть тестами первыми

Список не теоретический: каждый пункт — реально найденный и починенный дефект. В AI-only репозитории поедут снова именно они.

1. **Потолок яркости в disabled.** Ни один элемент внутри выключенного не ярче `--text-disabled` (включая `::placeholder` и семантические цвета).
2. **Выключенное не заметнее доступного.** Приглушённую поверхность в `disabled` получают только варианты, у которых своя поверхность есть; `ghost`/`secondary` её не приобретают, а рамка `secondary` гаснет цветом, но остаётся (это форма, не подсветка).
3. **Управляемый режим.** Пришёл колбэк — контрол показывает ровно переданное значение. Композиция: ряд передаёт колбэк вниз только если получил свой, а владея значением — обязан передать и `value`. Замерзший контрол ловили здесь трижды.
4. **Оптическая центровка по форме набора.** У цифр нет выносных, пятно сидит выше — числовой набор опускается сильнее прозы. Компенсация принадлежит группе, а не одному из соседей по базовой линии. Гейт обязан сравнивать ink-центр (canvas `actualBoundingBox*`), а не центр бокса: центры боксов сходились при явно кривой картинке.
5. **Ничьих пикселей нет.** Зазор между опциями принадлежит кнопкам, зона контрола растянута на высоту ряда. Проверять, что клик в любой точке ряда не вызывает чужое действие.
6. **Вложенных `<label>` нет.** Корень ряда — `div`; вложенный label даёт второе активационное событие и обходит гейт ⓘ.
7. **Токены, а не литералы.** Ни одного hex/rgba, `cubic-bezier`, литерального веса и интерлиньяжа в компонентах; примитивы `--c-*`/`--k-*` напрямую не используются.
8. **Валидация только там, где значение можно не дать или дать неверно.** У ChoiceRow её нет вовсе, у SwitchRow — предупреждение, а не ошибка; у Island нет валидации в принципе.
9. **Одинаковое выглядит одинаково.** Один смысл (значение в ряду, единицы, пилюля циклера) рисуется одним кодом — визуальные снапшоты обеих реализаций рядом.
10. **Капс и трекинг принадлежат надписи, а не кнопке.** Иначе `::before`-тултип наследует `text-transform` и подсказка выходит капсом.

## 6. Как потребляют сервисы (это определяет всё остальное)

Реши модель ДО настройки CI — от неё зависит, что в `dist/`:

- **Вариант A — статичные ассеты (минимум трения, под текущий рантайм).** Публикуем npm-пакет с `tokens.css`, `ds.css`, `svgs/`, `fonts/`, `support.js`, `*.dc.html`. Сервис подключает `<link>`/`<script>` и монтирует DC через `support.js`. Плюс: ноль переписывания. Минус: сервис обязан жить в том же DC-рантайме.
- **Вариант B — токены как пакет + компоненты как исходники.** `@banner-lab/tokens` (CSS + JS-константы, генерятся из `tokens.css` через Style Dictionary) отдельно; компоненты — вторым пакетом. Токенами можно пользоваться в любом стеке уже сейчас.
- **Вариант C — полноценная библиотека компонентов** (React/Web Components) — только если сервисы не на DC-рантайме. Это миграция (см. §2.4), не первый шаг.

**Рекомендация:** старт с **A + вынести токены как в B** (`@banner-lab/tokens`). Версионирование — **changesets** (семвер, автогенерация CHANGELOG, независимая публикация пакетов). Потребители пинят мажор; breaking-change пропа = мажор и запись ченджсета (проверяется гейтом из §5).

## 7. CI (.github/workflows/ci.yml) — красный блокирует мёрж

На каждый PR и пуш в main:
1. `npm ci`
2. `lint:tokens`, `lint:props`, `typecheck`
3. `test:unit` (vitest — логика `renderVals`: валидация, edge-кейсы, форматирование)
4. `test:smoke` (§4)
5. `test:a11y` — `pa11y-ci` по списку URL всех компонентов, стандарт **WCAG2AA**, ноль нарушений = гейт; плюс `@axe-core/playwright` внутри visual-тестов
6. `test:visual` — Playwright снапшоты каждого плейграунда в **обеих темах** (dark/light) и при `prefers-reduced-motion`; дифф > порога — фейл; апдейт снапшотов только явным коммитом
7. Артефакты: отчёты pa11y/axe и визуальные диффы прикладывать к прогону
8. Branch protection: запрет мёржа при красном, запрет прямого пуша в main, обязателен ченджсет (бот-проверка)

Матрицей гонять на нескольких браузерах (chromium обязателен; webkit/firefox желательно). Кэшировать `~/.npm` и браузеры Playwright.

## 8. Что ещё написать в репозитории (важно для AI-only)

- **`README.md`**: назначение, `npm run dev` → Сторибук, структура уровней, как потребитель подключает пакет, ссылка на живую витрину.
- **`CONTRIBUTING.md` (главный документ для AI)**: жёсткий workflow — «прочитай CLAUDE.md → меняй в src → `npm run verify` локально → все гейты зелёные → ченджсет → PR». Явно: **никогда не редактировать `support.js` вручную**, **не апдейтить визуальные снапшоты не глядя**, **новый компонент = smoke+unit+a11y+visual+запись в матрицу статусов**. Запрет литералов цвета/изингов. Definition of Done чек-лист.
- **`CLAUDE.md`**: переносится как есть; дополнить разделами о тестах и релизах.
- **`docs/` (или оставить в Сторибуке)**: Токены/темы, Доступность, UX-writing, Движение, матрица статусов — уже есть в витрине; в репо можно продублировать как MD для индексации.
- **ADR / RFC** (`docs/adr/`): решения фиксировать записями (напр. «почему остаёмся на DC-рантайме», «схема токенов», «политика семвера») — чтобы будущий AI не переигрывал уже принятое.
- **Матрица статусов** (stable/beta) — вынести в машиночитаемый `components.json`, из него же строить витринную таблицу и гейт «beta нельзя пометить stable без snapshot-теста + записи в CHANGELOG».
- **Контроль дрейфа витрины.** Storybook — единственный источник истины, и он уже расходился с кодом: описывал удалённый режим острова, ссылался на удалённый компонент Status, показывал в специмене уровень яркости, которого у компонента нет. Гейт: список компонентов и их пропсы витрина берёт из `api.json`/`components.json`, а не из рукописного текста; упоминание неизвестного компонента или токена — фейл.
- **Бюджеты**: контраст (все токен-пары текст/фон ≥ WCAG AA — отдельный скрипт-проверка), размер `dist/`, число зависимостей.
- **Renovate/Dependabot** + `npm audit` в CI — обновления зависимостей без человека.
- **PR-темплейт** с чек-листом гейтов.

## 9. Порядок для Claude Code (пошагово)

1. Создать репозиторий, положить файлы, разложить по `src/<уровень>/`, поправить пути в хелметах. Коммит 1.
2. `package.json` + `.nvmrc` + Vite dev-сервер; убедиться, что Сторибук открывается. Коммит 2.
3. **Smoke-тест (§4)** + Playwright. Зелёный — фундамент. Коммит 3.
4. `check-tokens` + `check-props` + генерация `types.d.ts` из `data-props`. Коммит 4.
5. Unit-тесты на `renderVals` ключевых компонентов: валидация Input/RowMsg (`touched`, punish-late / reward-early), Slider `set(v, exact)` (магнит принадлежит только перетаскиванию), управляемый режим Toggle/Checkbox/OptionGroup/Tabs/CycleButton/Disclosure, маппинг Badge `variant`×`tone`, сборка `rows` в Island. Коммит 5.
6. a11y (pa11y-ci) + visual (снапшоты dark/light/reduced-motion). Коммит 6.
7. `ci.yml` + branch protection + changesets + CONTRIBUTING/README/ADR. Коммит 7.
8. Опубликовать **только** `@banner-lab/tokens` — он не зависит от рантайма. **Компоненты на DC-рантайме не публиковать**: у системы ноль потребителей, и публикация создала бы связанность, из-за которой миграция на React (ROADMAP, Фаза 3) стала бы согласованным мажором во всех сервисах вместо простого сравнения с эталоном. Модель потребления (§6) и версию 1.0.0 определяем после миграции.

**Definition of Done переезда:** `npm run verify` зелёный локально и в CI; каждый компонент проходит smoke+a11y+visual в обеих темах; десять инвариантов из §5а покрыты тестами; `@banner-lab/tokens` опубликован. Пилот-сервис и публикация компонентов — после миграции на React (ROADMAP, Фаза 4).
